# RadioApple Reader — Phase 1 technical audit and architecture plan

Audited 7 November 2026. Keep Jekyll, Markdown and the current reader routes. Expand the generated catalog into a metadata-only discovery layer, with separate Work Search and tag-browsing views. Start Phase 2 with a local, reviewable PDF import pilot. The collection is large enough to justify automation, and the samples show why a plain-text batch conversion would be unreliable.

## 1. Current architecture

| Component | What the project does today | Plan |
| --- | --- | --- |
| Content and build | `_fics/` contains `radioapple.md` and `just-business.md`. Jekyll converts collection Markdown to HTML using Kramdown. Front matter contains `title`, `author`, `summary`, `rating`, `warning`, `category`, `fandom`, `relationship`, `characters`, `additionalTags`, and `language`. The template uses strings. `just-business` stores lists as comma-delimited strings and its summary as a YAML block scalar. `radioapple` has mostly blank metadata. | Keep Markdown, the existing field names, and current filenames. Add typed metadata and normalize legacy values when reading the catalog. |
| Catalog | Liquid iterates titled `.md` documents in `site.fics`, derives the ID from the output URL and serializes the eleven listed fields with `jsonify`. `index.html` always loads the resulting `fic-data/catalog.js` into `window.RADIOAPPLE_CATALOG`. The browser accepts IDs matching `[a-z0-9-]+`. The Works screen builds one DOM item per work, showing title, byline, fandom and summary. | Extend the Liquid projection. Build at most one page of result blurbs at a time. Add an explicit duplicate-ID check. |
| Work payload | `_layouts/fic-data.html` writes the entire rendered HTML string to `window.RADIOAPPLE_WORK` in `fic-data/<id>/work.js`. The browser requests only the selected work, reads and clears the global, and parses all its chapters. The old `story.js` has no active HTML reference. | Keep one lazy payload per work initially. Measure very large works before deciding whether to split by chapter. |
| Reader parsing | `app.js` parses the HTML in a template, drops executable or embedded elements, strips attributes from allowed elements and unwraps other tags. Paragraphs, emphasis, strong emphasis, horizontal rules and some other prose elements survive. Links lose their destinations and images are dropped. Top-level `H2` headings matching `Chapter N` or `Chapter N: Title` start chapters. With no markers the body is one chapter. Top-level `H3` labels `Notes`, `Text`, and `End Notes` switch sections. Only chapters with nonempty body text survive. Displayed numbering uses encounter order, so a skipped source chapter can be hidden by renumbering. | Keep the chapter contract. Validate order and counts before approving an import. Add structured notes or illustration support only where needed and tested against the reader. |
| Reader metadata | The reader uses `textContent` for title, author and summary, joins tag arrays for display, hides empty tag fields, reports parsed chapters as `n/?` and counts whitespace-delimited runs in body text. The summary displays Markdown markers literally. Browser storage holds reading appearance and font size. | Preserve legacy display and preferences. Use declared stats in discovery with explicit provenance. Treat the reader's current count and `/?` as presentation derived from the payload. |
| Navigation | The root and `index.html` show Works. Work links use `?fic=<id>`, with `#work`, `#chapters`, `#chapter-N` and `#chapter-N-text` for reader navigation. Bare legacy reader hashes redirect to the `radioapple` work if present. The Works link goes back to the library root. Tags are plain text. | Reserve `fic` and all existing hashes. Add query-driven discovery routes. Keep Back and a contextual return link useful after opening a work. |

## 4. Metadata schema

Use an additive front matter schema. Keep original labels and spelling in Markdown. Derive the runtime `id` from the existing basename and freeze it after adoption. New imports use `ao3-<work-id>` where the work's own source URL confirms that ID. A reviewed local work without a source ID can use `local-<digest>` allocated in the import manifest, with collision checks and a persistent mapping across revisions. Keep `radioapple` and `just-business` as their current route IDs. The archive ID and the local route ID serve different purposes.

| Field | Format and semantics |
| --- | --- |
| `schemaVersion` | Integer `2` for new files. Omitted means legacy. Reject unsupported versions at validation. |
| `title`, `author`, `summary` | UTF-8 strings. `author` is the full display byline and `summary` preserves paragraph breaks as a block scalar. Title is required for the current catalog. A missing title can be stored in staging for review. Missing byline and summary are empty. Preserve a source-displayed `Anonymous` value if present. |
| `creators` | Ordered list of `{ name, url? }` when individual bylines are known. Retain `author` for reader compatibility. A legacy byline can support text search without assuming it is one exact creator identity or splitting it on punctuation. |
| `rating`, `warning`, `category`, `fandom`, `relationship`, `characters`, `additionalTags` | Rating is a string or null. The other fields are ordered lists of display strings in v2. Empty arrays supply no filter values. Explicit `Not Rated`, `Creator Chose Not To Use Archive Warnings`, and `No Archive Warnings Apply` remain separate source values. |
| `language`, `languageCode` | Source language label plus optional known normalized code, such as `English` and `en`. Use a reviewed label-to-code table. No language detection from the story or folder. |
| `wordCount`, `wordCountSource` | Nonnegative integer and `archive` or `derived`. Prefer the export's count. A derived count uses a documented body-only algorithm and is visibly identified as such. Unknown is null. |
| `chaptersAvailable`, `chaptersPosted`, `chaptersTotal`, `completionStatus` | Positive counts or null. Available is the number verified in the local body. Posted and total come from the source fraction. `?` becomes null. Use `complete`, `in-progress`, or null. Infer completion from recognized source evidence, such as verified `18/18`. A verified export's `n/?` or `n/m` with `n < m` indicates in-progress. Missing local chapters are an import defect and do not change source completion. |
| `publishedAt`, `updatedAt`, `completedAt` | Quoted `YYYY-MM-DD` strings or null. Map each to its source label. For revised-date display and sorting, prefer a verified updated date. A completed or published date may be shown with its own label where update date is unavailable. Keep the Date Updated filter specific to known update dates. |
| `source` | Optional `{ archive, workId, url }`. Use `ao3` for the recognized export and a decimal string for its work ID. Keep the observed work URL after verifying the host and path. Keep source paths, checksums, review notes and import logs in the local manifest. |
| `stats`, `series`, `collections` | Optional stats object with observed nonnegative integer `hits`, `kudos`, `comments`, `bookmarks` and optional verified `asOf`. Zero is a real value. `series` is an optional ordered list of `{ title, position?, url? }`. `collections` can be retained as source labels where useful. Project them into discovery only when displayed or used. |

At import time, extract and validate display fields and typed source values. At Jekyll build time, project the allowlisted fields into the catalog using `jsonify`. At browser index time, normalize scalar/array variants into one typed model and build lookup keys using Unicode normalization, case folding and whitespace normalization. Preserve diacritics, punctuation and relationship separators in exact tag keys. Keep looser tokenization separate for text search. For existing tag strings, split only the fields known to use comma lists. Trim blanks and document that legacy boundaries are best effort. Existing fields and Markdown require no migration. Metadata backfills can be verified individually. A work with an empty tag field remains visible when unfiltered and has no positive match for that facet.

## 5. PDF importer design

1. **Scan and classify.** Recursively enumerate `.pdf` files in a stable order. Record relative path, byte size and SHA-256. Skip the known guide. Identify AO3 layouts from cover anchors, row layout and link targets, using the producer as a hint. Unknown formats enter review. Support selected files and a full-directory dry run in Phase 2, starting with the sampled pilot.
2. **Read positioned text and page objects.** Start with `pdfplumber` for characters, fonts, images, vector objects and link geometry. Use `pypdf` for outline destinations and an independent text check where needed. Use Poppler for targeted visual checks. Close page caches as work progresses and limit worker concurrency on long or image-heavy files. Consider PyMuPDF span/block extraction only if the pilot shows a speed or layout gap. Serialize YAML with a safe emitter and preserve UTF-8. [pdfplumber](https://github.com/jsvine/pdfplumber) · [pypdf text extraction](https://pypdf.readthedocs.io/en/stable/user/extract-text.html) · [PyMuPDF text recipes](https://pymupdf.readthedocs.io/en/latest/recipes-text.html).
3. **Extract metadata and ordered sections.** Read the cover through the end of the stats block, allowing continuation pages. Use link targets and bounds to group wrapped tags, including tags whose links cover multiple lines. Where links are unavailable, use label boundaries and verified delimiters. Preserve the displayed value even when the URI uses a different tag name. Detect heading styles and compare outline destinations when meaningful. Track preface, chapter summary, chapter opening notes, body, chapter end notes, work end notes, and ancillary links separately before serialization. Resolve ambiguities with rendered-page review.
4. **Emit compatible Markdown into staging.** Use `## Chapter N: Title` in verified source order and `### Notes`, `### Text`, `### End Notes` in the positions expected by the reader. For a compatible first pass, put work opening notes after the first chapter marker and work end notes at the end of the last chapter. Keep their distinct scope in the staging record. Chapter summaries can use a clearly labeled subsection in the chapter preface. An unnumbered source heading becomes the title of the corresponding verified ordinal. Escape literal Markdown syntax and lines that the reader might interpret as chapter or note markers. Join confirmed layout wraps and preserve author punctuation, spelling, paragraph boundaries, line breaks and emphasis. Carry meaningful links and images into review. The present reader cannot show them faithfully, so illustrated or link-dependent works require a resolution before promotion.
5. **Validate before promoting.** Compare parsed chapters against posted counts and verified headings. Account for every source page and any continuation. Check all nonempty prose spans are emitted exactly once, excluding classified boilerplate. Check suspected chapter gaps, repeated chunks, low text coverage, unexplained page images, NULs, replacement characters, unexpected ordering and substantial word-count discrepancies. A count difference is a signal because counting conventions vary. Compare independent extractors on flagged pages and inspect visual fixtures. Use the generated HTML and current reader to check that paragraphs, notes and chapters survive Jekyll conversion. Scans or unrecoverable text stay staged for source review. OCR can help locate evidence during review. The approved text must trace back to the source.
6. **Deduplicate and report.** Byte-identical input is one file identity regardless of name. Group separate copies by confirmed AO3 ID and compare chapters, metadata and ordered body fingerprints to detect variant snapshots. Preserve the reviewed work when snapshots conflict. For unidentified works, use title, creator and body similarity to propose a match for review. Save parser version, source hash and stable ID mapping in a manifest. The same source and parser version should produce identical Markdown bytes or skip an unchanged result. Write output through temporary files and atomic replacement, and reconcile the manifest on retries. Preserve manually edited files and report conflicts.

Use a per-run JSON Lines report and a readable summary. Each result should identify the relative source path, work ID if known, export profile, page count, detected chapter count, missing fields, duplicate or collision outcome, severity and relevant page numbers. Distinguish `ready`, `ready_with_missing_metadata`, `needs_review`, `failed`, `duplicate`, and `non_work`. Reserve a blocking review status for unreadable or potentially missing story content, unresolved chapters, incompatible media and identity conflicts. Blank optional metadata remains eligible. A work missing its display title can be extracted and staged, with title verification required for catalog admission. Avoid copying prose into logs.

The importer should produce a local staging library and a separate explicit promotion step for approved Markdown. Publication eligibility is independent of extraction quality. Keep source PDFs, private provenance, staged outputs and reports outside the publishing tree or explicitly excluded. A contributor's shared download and an author's public AO3 page are evidence of access. The two sampled repost restrictions are grounds to keep those works out of the public set. See the publication decision in Section 8.

## 6. Static search and navigation

Use one versioned, Jekyll-generated metadata catalog to start. Preserve the current JS output path and data compatibility while expanding the projection. The script format supports both normal hosting and the documented local `file:` entry point. With that compatibility requirement, avoid making JSON fetched over HTTP a dependency of the library. Keep summaries plain text at first and render data with `textContent`. When enabling summary formatting, pass it through a small allowlist. Use relative links and validate all IDs and external URL schemes. Keep body HTML exclusively in lazy work payloads.

- **Index once per load.** Use a map from work ID to normalized record, an exact per-type tag dictionary, and precomputed text fields for title, creator, tags, summary and language. Consider a bounded, separately measured projection of work-level notes in Phase 5 for closer Any Field behavior. Keep chapter prose and individual chapter notes out of discovery. A linear scan is adequate as the starting implementation. Add postings for typed facets and tokens when measured query cost warrants them.
- **Combine filters predictably.** Apply the current tag scope, text query and structured predicates together. Require every included typed tag and reject a work if it has any excluded tag. Use explicit filters for completion, language, one chapter, dates and inclusive bounds. Advanced strict inequalities keep their distinct meaning. Records with unknown values remain visible under All and do not satisfy positive filters for those values. Exclude removes works with a known match. Preserve a visible distinction between unknown warning information and a declared no-warning tag. Crossover filters use verified fandom-group mappings. Unknown relationships between fandoms remain unclassified.
- **Keep tag identity separate from text relevance.** Build facet keys from the tag group and normalized label. A reviewed alias map can join a variant to its canonical key while retaining the original display tag. Keep `/` and `&` distinct. In Other Tags, offer exact local values via autocomplete. Resolve a label present in multiple groups by asking the reader to choose a typed suggestion. An unrecognized tag needs clear feedback. Search within results can handle text matching. For Any Field, implement phrases, `-` exclusions, explicit `AND`/`OR`, and common trailing wildcards as a defined subset. Keep the documented same-field behavior for bare space-separated terms. List supported syntax and show an error for unsupported operators. Start relevance with deterministic weighting for title, creator, tags and summary.
- **Derive facets and pages from the same result model.** Sort and paginate the filtered result IDs before rendering. Use 20 items per page, preserve the result count and offer top and bottom pagination in tag browsing. Default tag sorting to latest known update, falling back to the latest documented source date for browse ordering. Default text search to relevance. Sort missing values last in either direction, and use `id` as the final tie-breaker. Show popularity sorts only when those values exist and identify them as snapshot data. Show top facet counts for the current result set as the first approximation. Keep applied values visible at zero and compare counts after conflicting filters with AO3 before finalizing the display.
- **Make applied state shareable.** Use `URLSearchParams` with a fixed set of modes and validated keys, for example `index.html?view=tag&tag=relationship%3Abilly+loomis%2Fstu+macher&include=rating%3Amature&minWords=500&page=2`. Use repeated parameters for includes and excludes, and omit defaults from canonical links. Tag and fandom links open a new scope. Clear Filters retains the scope, and a filter or sort change resets the page. Load and reload the same URL to reconstruct selections and results. Use real links for work and page navigation. If updating in place, use `pushState` for submitted state and handle `popstate` to preserve Back behavior. Restore list scroll and focus where practical. A contextual return link can use a validated, same-site discovery query. Keep copied work links usable without return state.

| Collection size | Expected behavior and scaling plan |
| --- | --- |
| Dozens | One catalog load, one normalization pass and a simple scan. Render only the current result page. |
| Hundreds | Same architecture. Cache normalized fields and measure bytes, query time, facet computation and rendering on a phone. Use per-tag postings if counting facets repeatedly becomes costly. |
| Thousands | Profile the 1,283-work upper bound and a larger representative fixture, with realistic summaries and tag fan-out. The current two-entry catalog averages about 1.3 KB per work uncompressed. Extrapolating from that small sample gives roughly 1.6 MB before adding v2 fields, and actual long summaries and tags can move the result substantially. Measure network and parsing separately. If indexing or filter work blocks interaction, move computation to a worker on supported hosting with a tested main-thread local fallback. If transfer dominates, compact repeated labels and keys, then consider a small all-work search index plus lazily loaded blurb details. Fandom-only sharding would still need a complete cross-fandom search index. |

Proposed Phase 6 budgets on a representative phone are under 500 KB compressed for the initial discovery data and under 150 ms from a warm filter submission to rendered results. Establish a cold-load baseline and measure at the actual collection size. A browsing session should request zero work body files until opening a work. If direct reader entry slows down due to catalog load, move its metadata into a small per-work resource and fetch the full catalog only in discovery. Measure download, parse and memory on the largest approved work before splitting the current chapter payload format.

## 8. Open decisions and release risks

- **Which works are eligible for the public gift site?** The requested Pages URL is a public distribution surface. Confirm the approved subset and whether the recipient needs a private library. Keep conversion and QA local until this is resolved. Where an author asks for the work to stay on AO3, keep it out of the public collection. GitHub's ordinary Pages configuration is public even for private repositories. [GitHub Pages visibility](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https).
- **What should happen to works with illustrations, image-based chapter markers, or essential links?** The default pilot can flag and hold them for review. A later decision is needed between supporting vetted local assets and keeping those works outside the published subset. Request a clean export or another authorized source only for flagged works that are wanted in the library.
- **Which phone and AO3 skin should define visual fidelity?** Use the logged-out default skin as the working reference. If the recipient primarily uses a different skin or a particular mobile browser, their screenshots or a short recording of browsing and filtering would resolve the remaining geometry and interaction questions.

Proceed with Phase 2 using a local, dry-run-first pilot. Use `Are we dating?`, `Voices`, and the 9-1-1 and Arcane samples to establish the normal path. Use the chapter structure and media cases from `Good Endings`, `Manacled`, and `Same` to exercise the review gates. Expand the batch once the pilot can explain every omission, preserve reader-visible prose and distinguish missing metadata from extraction failures.
